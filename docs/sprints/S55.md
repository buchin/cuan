   - Menerapkan mekanisme *graceful drain*: saat deployment berlangsung, worker menyelesaikan task in-flight hingga tuntas sebelum me-reload diri.
   - Menerapkan *self-update*: setelah task selesai, worker memeriksa ketersediaan binary baru pada disk dan melakukan graceful restart ke versi terbaru sebelum mengambil job berikutnya dari database queue.

     - **Attempt 1 (Base Run)**: 15 menit.
     - **Attempt 2 (First Requeue / Gap Fixable)**: 20 menit.
     - **Attempt 3+ (Final Requeue / Max Cap)**: 25 menit (batas tertinggi absolut).
   - Menggunakan terminasi bertahap: sinyal graceful `SIGTERM` dengan grace period toleransi, disusul eskalasi `SIGKILL` jika proses tidak merespons, serta pelepasan durable OS file lock.
   - Refactor modul runner dan launcher agar lean, modular, terpisah dari file supervisor monolitik (*god-file*), dan memiliki waktu kompilasi/uji sangat cepat (<10 detik).

## Spesifikasi Progressive Adaptive Timeout & Standar Lean Code

### 1. Progressive Adaptive Timeout
Untuk mengakomodasi variasi kompleksitas pekerjaan agen dan menghindari kegagalan prematur tanpa mengorbankan perlindungan terhadap *runaway process*, sistem menerapkan timeout bertingkat adaptif berdasarkan nomor percobaan (*attempt count*):

| Attempt | Durasi Timeout | Deskripsi Peruntukan |
|---------|---------------|----------------------|
| **Attempt 1 (Base)** | **15 Menit** | Eksekusi normal tugas awal. Cukup longgar untuk komputasi umum, analisis kode, dan targeted test. |
| **Attempt 2 (First Requeue)** | **20 Menit** | Requeue pertama akibat gap evaluasi DoD yang *fixable*. Diberikan tambahan durasi 5 menit untuk kompensasi perbaikan dan pengujian ulang. |
| **Attempt 3+ (Max Cap)** | **25 Menit** | Requeue kedua / percobaan lanjutan. Batas durasi tertinggi (*hard upper cap*) absolut untuk memberikan kesempatan terakhir penyelesaian tugas. |

- **Batas Maksimal Percobaan (Max Attempt Cap)**: Maksimal 3 kali percobaan eksekusi per task. Jika setelah percobaan ketiga kriteria DoD tetap tidak terpenuhi, sistem tidak melakukan requeue ulang, melainkan menandai status task sebagai `review` / `blocked` agar tidak terjadi perulangan tanpa akhir (*infinite loop*).
- **Protokol Terminasi Graceful Bertahap**:
  1. Pada saat batas waktu tercapai, konteks eksekusi dibatalkan (`context.WithTimeout`).
  2. Worker mengirimkan sinyal `SIGTERM` secara santun kepada proses child dan memberikan jendela toleransi (*grace period*) 20 detik untuk pelepasan resource secara rapi.
  3. Jika proses tidak berhenti dalam jendela toleransi, worker mengeksekusi sinyal tegas `SIGKILL` untuk memastikan proses mati dan melepaskan seluruh durable OS file locks.

### 2. Standar Lean Code & Modularitas
- **Dekomposisi God-File**: Memecah modul pengawasan monolitik yang terlalu besar menjadi beberapa file terfokus dengan tanggung jawab tunggal (misalnya: `runner.go`, `drain.go`, `updater.go`, dan `timeout.go`).
- **Zero Dead Code & Zero Bloat**: Tidak meninggalkan fungsi yang tidak terpakai (*dead code*), komentar usang, atau dependensi pihak ketiga yang tidak esensial.
- **Kompilasi & Targeted Test Kilat**: Kode terstruktur secara modular sehingga kompilasi dan eksekusi targeted unit test Go dapat berjalan tuntas dalam waktu kurang dari 10 detik.

## Risiko, Batasan & Mitigasi

1. **Risk: Kegagalan Self-Update Jika Binary Baru Belum Siap / Corrupt**:
   - *Dampak:* Worker mencoba me-reload binary yang belum selesai ditulis atau tidak memiliki izin eksekusi (`chmod +x`), menyebabkan crash daemon.
   - *Mitigasi:* Worker memverifikasi integritas file (keberadaan file, executable bit, dan validitas eksekusi versi via `runner --version`) sebelum melakukan handover proses. Jika tidak valid, worker tetap menggunakan binary yang ada dan mencatat error log.
2. **Risk: Infinite Loop pada Auto-Requeue DoD Evaluator**:
   - *Dampak:* Jika terjadi kegagalan permanen yang tidak dapat diperbaiki (misal dependensi eksternal rusak), sistem terus melakukan requeue tanpa henti.
   - *Mitigasi:* Sistem menerapkan batas tegas maksimal 3 kali attempt (`max_attempts = 3`). Setelah attempt ke-3, task otomatis dipindahkan ke status `review` atau `blocked` dengan penjelasan lengkap.
3. **Risk: Skrip Deployment Lama Membunuh Worker Aktif Secara Paksa**:
   - *Dampak:* Task in-flight terputus saat deployer memanggil `pkill` atau restart service sistem.
   - *Mitigasi:* Perbarui `scripts/deploy.sh` dan `scripts/activate-release.py` dengan mekanisme drain signal (misal membuat file flag `/tmp/cuan-drain` atau sinyal `SIGUSR1`) yang memberi tahu worker untuk menolak job baru dan keluar secara bersih setelah task aktif tuntas.
