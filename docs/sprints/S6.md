## Sprint goal dan demo outcome

### Sprint Goal
Membangun ekosistem Observabilitas, Health Probes, Telemetri Resource Server, dan Incident Alerting Hub multi-channel pada Cuan: memungkinkan pemantauan proaktif dan terus-menerus terhadap ketersediaan dan latensi aplikasi yang di-deploy (baik di local sandbox maupun remote BYOS VPS), pengumpulan metrik utilisasi CPU, RAM, dan Disk secara real-time dan hemat resource, pendeteksian otomatis insiden outage / degradasi layanan dengan threshold failure streaks dan latency evaluator, pengiriman notifikasi alert terenkripsi ke berbagai saluran komunikasi (Telegram Bot, Discord Webhook, Generic HTTP Webhook dengan HMAC SHA256 signature) dengan mekanisme anti-spam / cooldown cerdas, antarmuka visualisasi terpusat di Studio Dashboard (Observability Hub) dengan kartu metrik hidup, grafik utilisasi, modal konfigurasi alert channels berpanduan interaktif, serta staging E2E drill dan release gate dengan jaminan 100% data retention Sprint 1–5.

### Demo Outcome
1. Pengguna membuka Studio Dashboard di tab baru "Observability" (`/studio/observability`) dan melihat ringkasan status operasional: Uptime Score %, Total Monitored Deployments, Active Outages, dan Average Latency ms.
2. Pengguna melihat kartu telemetri resource server secara live yang menampilkan metrik CPU (%), Memory RAM (Used vs Total MB), dan Disk Storage (GB) untuk node server BYOS maupun deployment lokal.
3. Health Check Engine secara otomatis menjalankan probe periodik ke deployment aktif (HTTP status code, response time ms, consecutive failures), memperbarui status kesehatan (`healthy`, `degraded`, `unhealthy`).
4. Pengguna mendaftarkan channel notifikasi baru (Telegram Bot atau Discord Webhook) melalui modal Alert Channels, dengan kredensial tersimpan secara aman dalam format terenkripsi AES-GCM at-rest, lalu menguji kirim pesan via tombol "Test Alert" (notifikasi demo langsung muncul di aplikasi chat pengguna).
5. Saat aplikasi deployment mengalami kegagalan (simulasi crash / status 5xx / timeout) melampaui ambang batas kegagalan (consecutive failures >= 3), Incident Alert Dispatcher mencatat record insiden baru berstatus `firing` dan menembakkan pesan darurat berisi detail error dan tautan langsung ke Studio.
6. Ketika aplikasi pulih kembali (`healthy`), Incident Alert Dispatcher mendeteksi transisi recovery, memperbarui insiden menjadi `resolved`, dan mengirimkan notifikasi pemulihan (recovery notification) hijau ke seluruh channel terkait.

## Target pengguna dan nilai produk

### Persona Target Market
1. **Solo Developer & Indie Hackers:** Mengembangkan dan mengoperasikan produk digital/SaaS mandiri tanpa tim DevOps. Sangat membutuhkan ketenangan pikiran (*peace of mind*) dengan notifikasi instan langsung ke ponsel (Telegram/Discord) begitu server bermasalah, sebelum calon pembeli atau pelanggan komplain di media sosial.
2. **Freelance & Digital Agencies:** Mengelola puluhan aplikasi klien dengan SLA ketat. Membutuhkan visibilitas terpadu di satu dashboard untuk memantau uptime seluruh situs klien, mendeteksi server VPS yang hampir kehabisan RAM/Disk, dan menyajikan laporan keandalan sistem kepada klien secara profesional.
3. **Product Founders & Backers:** Memerlukan transparansi kondisi infrastruktur aplikasi tanpa harus menginstal agent monitoring pihak ketiga (seperti Datadog atau NewRelic) yang rumit, mahal, dan memberatkan kapasitas server kecil (1 GB RAM VPS).

### Pertimbangan Kepuasan Target Market (DoD Focus)
- **Zero-Agent / Low-Overhead Architecture:** Probing kesehatan dilakukan via HTTP probe ringan dari control plane Cuan dan pembacaan metrik BYOS via telemetry query non-invasif tanpa membebani CPU server target.
- **Instant Outage Alerting via Everyday Tools:** Integrasi langsung ke aplikasi chat harian developer (Telegram Bot dan Discord Webhook) serta Webhook kustom dengan verifikasi signature HMAC untuk integrasi webhook otomasi (Zapier/Make/n8n).
- **Intelligent Anti-Spam & Deduplication:** Dilengkapi threshold evaluator (deteksi setelah 3x consecutive failures), cooldown window, dan pencegahan flapping agar pengguna tidak dibanjiri spam notifikasi saat jaringan berfluktuasi sesaat.
- **At-Rest AES-GCM Security:** Seluruh kredensial sensitif seperti token Telegram Bot dan URL Discord Webhook dienkripsi menggunakan AES-GCM 256-bit dan disanitasi dari DTO publik.
- **1-Click Test & Diagnostic Feedback:** Setiap channel notifikasi dilengkapi tombol "Test Alert" dengan visual feedback seketika untuk memvalidasi konfigurasi webhook/token sebelum diaktifkan dalam mode produksi.

## Fondasi teknis dan arsitektur

- **Backend:** Go (Golang) menggunakan `net/http` dan router `chi/v5`.
- **Database:** PostgreSQL dengan skema aditif migrasi `000011_observability_alerts.up.sql`:
  - `health_checks`: id, deployment_id (FK deployments(id) ON DELETE CASCADE), url, status (healthy/degraded/unhealthy), last_checked_at, last_status_code, response_time_ms, consecutive_failures, created_at, updated_at, dan indeks.
  - `server_metrics`: id, server_id (FK servers(id) ON DELETE SET NULL), deployment_id (nullable, FK deployments(id) ON DELETE CASCADE), cpu_percent, memory_used_mb, memory_total_mb, disk_used_gb, disk_total_gb, recorded_at, dan indeks.
  - `alert_channels`: id, project_id, type (telegram/discord/webhook), name, config_encrypted, is_active, created_at, updated_at, dan indeks.
  - `alert_incidents`: id, project_id, target_type, target_id, title, message, status (firing/resolved), triggered_at, resolved_at, dan indeks.
  - Menjamin 100% retensi data Sprint 1 (`owners`, `projects`, `tasks`), Sprint 2 (`sponsors`, `sponsorship_orders`), Sprint 3 (`deployments`, `deployment_logs`), Sprint 4 (`servers`), dan Sprint 5 (`custom_domains`).
- **Store & Repository Observabilitas (`internal/db/observability.go`):**
  - Model `HealthCheck`, `ServerMetric`, `AlertChannel`, `AlertIncident` dan DTO tersanitasi.
  - Interface `ObservabilityRepository` beserta implementasi `SQLObservabilityRepository` dan thread-safe `MemoryObservabilityRepository`.
- **Health Check Engine & Automated Poller (`internal/observability/health.go`):**
  - HTTP/HTTPS probing engine dengan konfigurasi timeout, status code evaluation, response time measurement, dan streak failure counter.
  - Worker pool background poller dengan lifecycle start/stop yang terkontrol.
- **Resource Metrics Collector (`internal/observability/metrics.go`):**
  - Collector metrik telemetri local runner (cgroup/host resource) dan remote BYOS server (SSH probe metrics).
- **Incident Alert Dispatcher (`internal/observability/alerts.go`):**
  - Threshold evaluator, state tracker (firing vs resolved), cooldown window, dan dispatchers:
    - Telegram Bot API: pesan berformat Markdown dengan emoji status dan link Studio.
    - Discord Webhook: rich embed cards (merah untuk outage, hijau untuk resolved).
    - Generic Webhook: JSON payload standar dengan header `X-Cuan-Signature: sha256=...`.
  - Enkripsi kredensial token dan webhook URL menggunakan AES-GCM 256-bit (`internal/crypto`).
- **Frontend Studio UI (`web/src/components/studio/ObservabilityView.tsx` & `AlertChannelsModal.tsx`):**
  - React + TypeScript + Tailwind CSS + shadcn/ui.
  - Dashboard ringkasan uptime, tabel status deployment health, live resource gauges, riwayat insiden, dan form pendaftaran alert channel.

## Infrastruktur, routing, dan staging gate

1. **Host & Port:**
   - Stable: Port `8080` (reverse proxy Caddy HTTPS / API Production).
   - Staging: Port `8081` (Compose project terisolasi, database terpisah).
2. **Data Retention & Compatibility Gate:**
   - Migrasi `000011_observability_alerts.up.sql` bersifat murni aditif tanpa mengubah struktur kolom tabel Sprint 1–5.
   - Foreign key cascading `ON DELETE CASCADE` memastikan jika suatu deployment dihapus, record health checks dan metrics terkait dibersihkan secara otomatis tanpa meninggalkan orphan records.
   - Rollback migrasi `000011_observability_alerts.down.sql` membersihkan seluruh tabel baru (`health_checks`, `server_metrics`, `alert_channels`, `alert_incidents`) beserta indeksnya dengan aman.
3. **Audit Keamanan & Anti-Spam Gate:**
   - Kredensial webhook URL dan bot token tidak boleh disimpan dalam plaintext; wajib menggunakan AES-GCM 256-bit at-rest.
   - DTO publik menyamarkan isi kredensial (misalnya token bot hanya menampilkan 4 karakter awal/akhir, atau tidak diekspos sama sekali pada JSON response).
   - Rate limiting dan cooldown window (minimal 5 menit) diimplementasikan untuk mencegah pembanjiran pesan saat outage berulang dalam rentang waktu singkat.

## Out of scope eksplisit

- Distribusi agent biner pihak ketiga (e.g. Prometheus Node Exporter / Telegraf / Datadog Agent) yang di-push ke server target — Cuan menggunakan HTTP health probe dan lightweight remote SSH telemetry runner.
- OpenTelemetry Distributed Tracing (APM span tracing mikro-level ke dalam runtime kode user) — fokus Sprint 6 adalah endpoint availability, service health, and system resource telemetry.
- Telepon darurat otomatis (SMS / voice call paging via Twilio/PagerDuty) — saluran notifikasi difokuskan pada Telegram, Discord, dan Generic HMAC Webhook.
- Log aggregation skala petabyte (seperti Elasticsearch / ClickHouse cluster) — deployment logs tetap dikelola via ring-buffer deployment_logs bawaan Sprint 3.

## Risiko dan respons

| Risiko | Dampak | Respons / Mitigasi |
| --- | --- | --- |
| Flapping Health Checks (layanan up-down berulang cepat) | Banjir notifikasi berlebihan ke chat developer (alert fatigue) | Evaluator mengharuskan 3x consecutive failures sebelum `firing`, dan streak consecutive successes sebelum `resolved` |
| Kebocoran token Bot Telegram atau URL Discord Webhook | Pihak ketiga dapat mengirim pesan palsu ke channel user | Kredensial disimpan terenkripsi AES-GCM 256-bit at-rest dan disanitasi dari respons publik DTO |
| SSH latency / timeout saat membaca metrik server BYOS | Poller thread macet dan memblokir pengumpulan metrik lain | Non-blocking telemetry runner dengan bounded timeout (maks 5s) per probe |
| Regresi skema database terhadap data Sprint 1–5 | Gangguan operasional pada data deployment, domain, atau server | Skema murni aditif tabel baru `health_checks`, `server_metrics`, `alert_channels`, `alert_incidents` dengan foreign key cascading |
