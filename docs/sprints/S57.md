## Outcome Sprint & Kesepakatan PO & SM

**Outcome:** Menghadirkan umpan balik tugas secara seketika (*real-time task feedback*) dan visibilitas menyeluruh (*end-to-end observability*) yang ramah pengguna awam pada antarmuka Cuan, sehingga pemilik usaha kecil dan pengelola toko online (*non-developer*) dapat memantau pengerjaan tugas oleh agen cerdas secara transparan tanpa rasa cemas (*zero guesswork & total peace of mind*). Sprint ini mengintegrasikan floating live progress chip dan completion card pada tampilan obrolan (Chat/Inbox), notifikasi audio chime dan lencana judul peramban (*document title badge*) di latar belakang, widget indikator kesehatan worker `cuan-runner` di menu Pengaturan, mempertahankan konfigurasi timeout adaptif yang terbukti stabil dari Sprint 56, serta menegakkan disiplin kode ramping (*lean & modular*) dan sinkronisasi berkala ke dokumentasi teknis serta Landing Page publik.

1. **Real-Time Task Progress Banner & Completion Card di Chat UI**:
   - Memperbarui antarmuka obrolan (`web/src/features/inbox/InboxView.tsx`) agar secara reaktif melacak tugas-tugas aktif yang terikat pada percakapan saat ini (`activeConversationTasks`).
   - Menyajikan *floating live progress chip* saat tugas berada dalam status antrean (`queued`) atau pengerjaan (`running`), menampilkan durasi berjalan, nama agen pelaksana, dan status tahapan tanpa mengacaukan riwayat percakapan.
   - Menyematkan kartu hasil penyelesaian instan (*actionable completion card*) saat tugas mencapai status selesai (`done`) atau tinjauan (`review`), lengkap dengan ringkasan hasil berbahasa bisnis, status kelulusan kriteria, dan tombol aksi untuk langsung membuka artefak atau melanjutkan instruksi.
2. **Background Audio Chime & Document Title Notification Badge**:
   - Menghadirkan notifikasi audio chime harmonis menggunakan Web Audio API murni (tanpa ketergantungan file aset eksternal yang rentan 404) saat tugas di latar belakang berhasil diselesaikan.
   - Menyediakan mekanisme *graceful zero-friction fallback*: bila izin autoplay audio dibatasi oleh browser, sistem otomatis beralih menampilkan lencana visual dinamis pada tab peramban (misalnya `(1) Tugas Selesai! - Cuan`).
   - Menerapkan interval polling adaptif (3–5 detik) yang hanya aktif saat ada tugas *in-flight*, dan beralih ke mode hemat daya (*idle backoff*) saat tidak ada tugas berjalan guna menjaga performa browser dan server tetap ringan.
3. **Worker Observability & Health Indicator di Pengaturan**:
   - Menyediakan endpoint ringkas dan berkinerja tinggi pada backend Go (`internal/server/routes_system.go`) yang melaporkan status kesehatan daemon `cuan-runner` (status aktif/inaktif, kedalaman antrean database, dan waktu heartbeat terakhir).
   - Menambahkan widget status kesehatan worker di menu Pengaturan Cuan (`web/src/features/settings`), menyajikan indikator visual sederhana (Hijau = Normal/Siap, Kuning = Sedang Memproses, Merah = Butuh Perhatian) sehingga pemilik bisnis dapat memastikan kesiapan sistem toko mereka tanpa perlu membuka terminal Linux atau akses server VPS.
4. **Preservasi Eskalasi Timeout Adaptif & Protokol Grace Period**:
   - Mempertahankan alokasi waktu timeout optimal yang telah dibuktikan pada Sprint 56:
     - Agent Chat CLI: Execution timeout 360s (6 menit), direct coordinator recovery 120s (2 menit), lifecycle context timeout 10 menit.
     - Agent Terminal / cuan-runner: Attempt 1 (25 menit), Attempt 2 (35 menit), Attempt 3+ (45 menit hard cap), termination grace period 30 detik (SIGTERM -> SIGKILL), dan terminal session idle timeout 30 menit.
5. **Aturan Wajib Room (Mandatory Standards)**:
   - **Kode Lean & Modular**: Seluruh penambahan kode di frontend dan backend wajib terisolasi, bebas dari file monolitik tak terkendali, dan pengujian unit terarah (*targeted test*) wajib tuntas dalam waktu <10 detik.
   - **Sinkronisasi Dokumentasi & Landing Page**: Seluruh penambahan kapabilitas real-time feedback, notifikasi audio, dan worker observability wajib didokumentasikan di `docs/` serta dipublikasikan pada Landing Page (`web/src/features/landing/LandingPage.tsx`).

## Spesifikasi Konfigurasi Timeout Baru, Polling Adaptif & Standar Lean Code

### 1. Matriks Alokasi Waktu Timeout

| Layer Eksekusi | Parameter / Skenario | Konfigurasi Default | Toleransi / Grace | Rationale Bisnis & Pengguna |
|----------------|----------------------|---------------------|-------------------|-----------------------------|
| **Agent Chat CLI** | Default Execution Timeout | **360s (6 menit)** | - | Ruang waktu yang aman bagi pemrosesan instruksi analitis agen tanpa terputus di tengah jalan. |
| **Agent Chat CLI** | Direct Coordinator Recovery | **120s (2 menit)** | - | Waktu stabilisasi parsing luaran koordinasi multi-agent. |
| **Agent Chat CLI** | Chat Lifecycle Context | **10 menit** | - | Context HTTP server tetap terjaga selama putaran interaksi panjang. |
| **Worker Terminal** | Attempt 1 (Base Run) | **25 menit** | 30s SIGTERM | Komputasi awal pembuatan kode, riset berkas, dan eksekusi tugas. |
| **Worker Terminal** | Attempt 2 (First Requeue) | **35 menit** | 30s SIGTERM | Kompensasi perbaikan saat pengujian awal membutuhkan penyesuaian. |
| **Worker Terminal** | Attempt 3+ (Hard Cap) | **45 menit** | 30s SIGTERM | Batas atas absolut sebelum penyerahan hasil transparan ke ruang obrolan. |
| **Terminal Session** | Idle Timeout | **30 menit** | - | Mencegah sesi interaktif mati saat pengguna sedang mereviu berkas. |
| **Frontend Poller** | In-Flight Task Polling | **3–5 detik** | - | Umpan balik progres cepat dan reaktif saat tugas sedang diproses. |
| **Frontend Poller** | Idle Polling Backoff | **15–30 detik** | - | Menghemat bandwidth dan sumber daya server saat tidak ada aktivitas tugas. |

### 2. Protokol Notifikasi & Graceful Fallback

1. **Web Audio Chime Synthesizer**:
   - Dihasilkan secara dinamis menggunakan `AudioContext` browser murni melalui kombinasi dua gelombang sinus frekuensi harmonis (C6 = 1046.5 Hz dan E6 = 1318.5 Hz) dengan peluruhan eksponensial (*exponential decay*) 0.4 detik yang ramah dan menenangkan.
   - Tidak memerlukan pengunduhan berkas audio biner eksternal (`.mp3` atau `.wav`), sehingga kebal terhadap kegagalan jaringan atau masalah aset CORS.
2. **Zero-Friction Autoplay Fallback**:
   - Jika pengguna belum berinteraksi dengan dokumen dan browser memblokir audio (`AudioContext was not allowed to start`), sistem menangkap pengecualian (*promise catch*) secara senyap tanpa menghasilkan error ke konsol pengguna.
   - Sistem secara otomatis mengaktifkan fallback visual seketika: memodifikasi `document.title` menjadi format `(1) Tugas Selesai! - Cuan` serta mengembalikan judul asli saat tab difokuskan kembali oleh pengguna (`window.onfocus`).

### 3. Standar Lean Code & Modularitas

- **Struktur Kode Terisolasi**: Komponen banner progres, completion card, utilitas audio, dan widget kesehatan worker dipisahkan ke dalam berkas modular khusus dengan batasan tanggung jawab yang ketat (*single responsibility*).
- **Pengujian Unit Kilat (<10s)**: Pengujian unit terarah (*targeted test*) pada backend Go dan frontend Vitest wajib tuntas di bawah 10 detik.
- **Zero Bloat & Zero Dead Code**: Tidak ada pustaka tambahan yang berlebihan, variabel usang, atau komponen duplikat yang ditinggalkan dalam repositori.

## Risiko, Batasan & Mitigasi

1. **Risk: Kebijakan Autoplay Browser Memblokir Web Audio Chime**:
   - *Dampak:* Browser menolak inisialisasi audio sebelum ada interaksi klik/ketik langsung oleh pengguna di jendela tab tersebut, menyebabkan audio chime gagal berbunyi.
   - *Mitigasi:* Menginisialisasi `AudioContext` secara malas (*lazy initiation*) saat ada interaksi pertama di antarmuka obrolan, membungkus panggilan play dalam `try-catch` senyap, serta menyediakan fallback visual seketika berupa kedipan lencana judul peramban (*document title notification badge*).
2. **Risk: Polling Berulang Menimbulkan Beban Berlebih pada API Server**:
   - *Dampak:* Interval polling yang terlalu rapat saat banyak pengguna aktif dapat meningkatkan penggunaan CPU dan lalu lintas database Cuan.
   - *Mitigasi:* Menerapkan *adaptive polling*: interval 3–5 detik hanya dijalankan saat terdeteksi setidaknya satu tugas *in-flight* (`queued` atau `running`) yang relevan dengan percakapan aktif; bila semua tugas selesai atau tab berada dalam kondisi tidak terlihat (*visibilityState: hidden*), interval melambat otomatis (*exponential backoff* hingga 15–30 detik).
3. **Risk: Lonjakan Render Ulang (*Re-render Storm*) di Tampilan Obrolan Chat**:
   - *Dampak:* Komponen `InboxView.tsx` yang besar dapat mengalami penurunan performa rendering jika polling status memperbarui state global secara sembarangan.
   - *Mitigasi:* Mengisolasi state progres tugas ke dalam selector memoized terarah (`activeConversationTasks`) dan merender banner serta completion card sebagai sub-komponen terisolasi yang hanya me-render ulang dirinya sendiri tanpa memicu render ulang daftar pesan historis obrolan.

## Out-of-Scope Eksplisit

- **Infrastruktur WebSocket Stateful / Socket.IO Cluster**: Antarmuka tetap mengandalkan arsitektur REST dengan interval polling adaptif yang jauh lebih sederhana, hemat memori, tahan terhadap putus koneksi jaringan seluler, dan ramah terhadap proksi/CDN.

- **Perombakan Layout Total Antarmuka Obrolan**: Tampilan obrolan yang ada tetap dipertahankan; perubahan difokuskan secara presisi pada penyematan floating progress chip dan completion card.
