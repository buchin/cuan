## Sprint goal dan demo outcome

### Sprint Goal
Membangun ekosistem Project Studio berparadigma Project-Centric pada Cuan: menghadirkan Discussion Rooms terisolasi per proyek (`project_rooms`), sistem perpesanan multi-aktor terstruktur dengan dukungan threading reply (`project_messages`), task board terintegrasi dengan acceptance criteria checklist (`project_tasks`), kapabilitas masa depan (future-proof) untuk hierarki fan-out (`parent_task_id`), pengelompokan batch multi-project (`batch_id`), dan tag selector array (`tags`), antarmuka Studio interaktif di Web UI, serta pelaksanaan staging E2E drill dan official dogfooding / production launch di `cuan.dojo.cc` dengan jaminan 100% retensi data historis Sprint 1–6.

### Demo Outcome
1. Pengguna membuka Studio Dashboard untuk suatu project (`/studio/projects/:id`) dan melihat menu terpadu "Discussions" dan "Tasks".
2. Pengguna membuat ruang diskusi topik spesifik (`project_rooms`), berinteraksi secara real-time via pesan (`project_messages`), dan membuat balasan berutas (*threaded reply* via `reply_to_id`).
3. Pengguna dan agen AI dapat menyuling (*distill*) hasil kesepakatan obrolan menjadi tugas terstruktur (`project_tasks`) lengkap dengan DoD checklist, status, dan prioritas.
4. Pengguna memanfaatkan kemampuan fan-out hierarchy (`parent_task_id`) untuk mengelola dekomposisi tugas besar menjadi subtasks, pengelompokan batch multi-project (`batch_id`), serta pencarian tugas berbasis tag selector (`tags` seperti `["wordpress", "adsense"]`).
5. Instance produksi di `cuan.dojo.cc` berhasil menerapkan migrasi database 000012 tanpa downtime dan 100% data Sprint 1–6 (Owner, Projects, Tasks, Sponsors, Deployments, Servers, Domains, Health Checks & Incidents) terverifikasi utuh.

## Target pengguna dan nilai produk

### Persona Target Market
1. **Solo Developer & Indie Hackers:** Mengoperasikan banyak produk mandiri. Membutuhkan ruang komunikasi dan pelacakan task yang melekat langsung di dalam repository project tanpa harus berpindah-pindah aplikasi (seperti Jira, Trello, Discord, atau Notion).
2. **AI-Assisted Engineering Teams:** Agen otonom dan manusia berkolaborasi dalam satu ruang obrolan. Agen dapat membaca konteks diskusi dan memecah perencanaan sprint menjadi tugas terarah dengan DoD checklist.
3. **Multi-Project Operators & Agency Leads:** Mengelola puluhan situs klien (e.g. niche affiliate/AdSense, WP multisite). Memerlukan pengelompokan tugas lintas-proyek secara batch (`batch_id`) dan klasifikasi fungsional melalui tag selector (`tags`).

### Pertimbangan Kepuasan Target Market (DoD Focus)
- **Zero-Friction Project Context:** Seluruh percakapan dan backlog tersimpan dalam satu konteks proyek yang jelas, menghilangkan kebingungan konteks antar aplikasi.
- **Future-Proof Fan-Out & Batch Architecture (PO Approved Option A):** Skema tabel `project_tasks` sejak awal mengakomodasi hierarki dekomposisi (`parent_task_id`), grup batch multi-project (`batch_id`), dan tag JSONB (`tags`) sehingga aman dari migrasi ulang di masa depan.
- **Threaded Communication & Audit Trail:** Percakapan mendukung pesan bersarang (`reply_to_id`), author identity (`user`, `agent`, `system`), dan pencatatan waktu yang presisi.
- **100% Data Retention Guarantee:** Skema database murni aditif; data historis operasional sejak Sprint 1 tidak pernah rusak atau teralterasi.

## Fondasi teknis dan arsitektur

- **Backend:** Go (Golang) menggunakan router `chi/v5` dan `database/sql` PostgreSQL 16.
- **Database Schema (`migrations/000012_project_discussions_tasks.up.sql`):**
  - `project_rooms`: `id` (UUID PK), `project_id` (FK `projects(id)` ON DELETE CASCADE), `title` (VARCHAR(255)), `topic` (TEXT), `created_at`, `updated_at`, dan indeks.
  - `project_messages`: `id` (UUID PK), `room_id` (FK `project_rooms(id)` ON DELETE CASCADE), `author_type` (VARCHAR(50): user/agent/system), `author_id` (VARCHAR(255)), `author_name` (VARCHAR(255)), `content` (TEXT), `reply_to_id` (nullable UUID FK self), `created_at`, `updated_at`, dan indeks.
  - `project_tasks`: `id` (UUID PK), `project_id` (FK `projects(id)` ON DELETE CASCADE), `room_id` (nullable UUID FK `project_rooms(id)` ON DELETE SET NULL), `title` (VARCHAR(255)), `description` (TEXT), `status` (VARCHAR(50): backlog/doing/review/done), `priority` (VARCHAR(50): low/normal/high/urgent), `dod_checklist` (JSONB), `assignee_id` (nullable VARCHAR(255)), `parent_task_id` (nullable UUID FK self), `batch_id` (nullable VARCHAR(255)), `tags` (JSONB array), `created_at`, `updated_at`, dan indeks (termasuk GIN index pada `tags`).
- **Repository Layer (`internal/db/project_studio.go` & `internal/db/db.go`):**
  - Interface `ProjectStudioRepository` dengan dukungan CRUD lengkap untuk Rooms, Messages, Tasks, hierarki fan-out, pencarian batch, dan filtering tags.
  - Implementasi PostgreSQL `SQLProjectStudioRepository` dan thread-safe in-memory `MemoryProjectStudioRepository` untuk unit tests dan mock mode.
  - Pendaftaran terpusat pada container `db.Repositories`.
- **Frontend Studio UI:** React + TypeScript + Tailwind CSS + shadcn/ui di `web/src/components/studio/`.

## Risiko dan respons

| Risiko | Dampak | Respons / Mitigasi |
| --- | --- | --- |
| Deep nesting pada hierarki fan-out (`parent_task_id`) menyebabkan cyclic reference | Query rekursif tak berujung (infinite loop) | Batasi kedalaman fan-out maksimal 2 tingkat (Epic -> Subtask) pada layer validasi |
| Data chat bertumbuh sangat cepat pada project aktif | Beban query history message | Paging / limit-offset pada endpoint listing pesan serta indeks `idx_project_messages_created_at` |
| Migrasi 000012 mengganggu relasi `projects` eksisting | Potensi error pada data historis Sprint 1–6 | Foreign key menggunakan `VARCHAR(64)` yang cocok persis dengan tipe primary key `projects(id)` eksisting |
