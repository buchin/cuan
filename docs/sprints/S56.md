**Outcome:** Menuntaskan pemisahan penuh (*full cutover*) eksekusi tugas ke worker daemon mandiri `cuan-runner` sehingga pengerjaan tugas dari chat maupun terminal sepenuhnya terisolasi dari proses web server dan kebal interupsi deployment (*zero interrupted work*), menyempurnakan siklus hidup deployment dengan mekanisme *auto-cleanup drain* dan *auto-restart worker*, mengeskalasi alokasi waktu timeout secara adaptif pada layer Chat CLI (3m -> 6m, context 10m) maupun Worker Terminal (25m -> 35m -> 45m cap, grace period 30s) untuk mencegah kegagalan tugas prematur, serta menghadirkan *intelligent DoD requeue loop* dengan transparansi batas percobaan (*limit transparency*) yang proaktif menyapa ruang obrolan (*multi-room proactive chat*) saat batas tercapai demi kenyamanan pemilik usaha UMKM non-developer (*zero-friction & zero-jargon*).

## Kesesuaian Target Market (UMKM, Pemilik Toko Online & Solopreneur)

Produk Cuan dibangun untuk pemilik usaha kecil, pengelola toko online, dan wirausahawan mandiri di Indonesia yang tidak memiliki latar belakang teknis pemrograman (*non-developer*). Mereka ingin mendelegasikan tugas bisnis harian (pembuatan materi promosi, rekap transaksi, integrasi email toko, pembuatan katalog) semudah bercakap-cakap di WhatsApp atau aplikasi pesan instan.

Solusi arsitektur dan peningkatan pada Sprint 56 secara langsung menjawab kebutuhan riil mereka:

1. **Delegasi Tugas Tanpa Rasa Cemas (*Zero Interrupted Work*)**:
   - Pengusaha sering kali menjalankan tugas pembuatan konten atau rekapitulasi yang memakan waktu belasan menit. Di masa lalu, jika sistem melakukan rilis pembaruan, proses tersebut dapat terputus di tengah jalan.
   - Dengan cutover penuh ke daemon mandiri `cuan-runner` yang terpisah dari web server, serta auto-undrain deploy hook yang mulus, pembaruan aplikasi di server berlangsung senyap tanpa mengganggu pekerjaan yang sedang dikerjakan agen untuk toko mereka.
2. **Waktu Eksekusi Proporsional (*No Premature Timeout*)**:
   - Tugas analisis mendalam atau penulisan kode solusi sering kali membutuhkan waktu komputasi yang lebih dari 3 menit. Timeout yang terlalu sempit menyebabkan agen gagal memberikan respons sebelum sempat menyelesaikan riset.
   - Eskalasi timeout Chat CLI menjadi 6 menit (dengan context 10 menit) serta Progressive Timeout terminal hingga 45 menit memberikan ruang napas yang cukup bagi agen untuk menyelesaikan pekerjaan berkualitas tinggi tanpa kegagalan prematur.
3. **Komunikasi Ramah Bisnis & Transparansi Batas (*Zero-Jargon & Limit Transparency*)**:
   - Jika suatu tugas menemui kendala setelah 3 kali percobaan revisi otomatis, pemilik bisnis berhak mengetahui situasinya secara jelas tanpa dibingungkan oleh istilah teknis seperti `exit code 137`, `context deadline exceeded`, atau `DoD evaluator mismatch`.
   - Multi-Room Proactive Notifier secara proaktif menyapa ruang obrolan tempat tugas didelegasikan (`q.RoomID` dan `t.SourceRoomID`) dengan pesan hangat, menjelaskan bagian yang sudah beres, menguraikan kendala yang tersisa dalam bahasa bisnis sederhana, dan menyajikan opsi langkah praktis berikutnya.
4. **Efisiensi Sumber Daya & Operasional Ramping (*Lean & Cost-Effective*)**:
   - Pelaku UMKM membutuhkan perangkat lunak yang hemat biaya hosting. Dengan standar kode modular dan lean, konsumsi RAM dan CPU di server VPS tetap terjaga rendah, memastikan performa aplikasi responsif dengan biaya infrastruktur yang terjangkau.

## Spesifikasi Konfigurasi Eskalasi Timeout Baru & Standar Lean Code

### 1. Perbandingan Alokasi Waktu Timeout

| Layer Eksekusi | Parameter / Skenario | Konfigurasi Lama | Konfigurasi Baru (Sprint 56) | Tujuan & Rasional Bisnis |
|----------------|----------------------|------------------|------------------------------|--------------------------|
| **Agent Chat CLI** | Default Execution Timeout | 180s (3 menit) | **360s (6 menit)** | Memberikan waktu memadai bagi agen chat untuk reasoning dan tooling tanpa timeout. |
| **Agent Chat CLI** | Direct Coordinator Recovery | 60s (1 menit) | **120s (2 menit)** | Recovery fallback parsing JSON/format respons lebih stabil pada respons panjang. |
| **Agent Chat CLI** | Chat Lifecycle Context | 5 menit | **10 menit** | Menjaga context HTTP background tetap hidup selama multi-turn agent invocation. |
| **Worker Terminal** | Attempt 1 (Base Run) | 15 menit | **25 menit** | Alokasi ideal untuk komputasi awal, analisis codebase, dan implementasi fitur. |
| **Worker Terminal** | Attempt 2 (First Requeue) | 20 menit | **35 menit** | Kompensasi waktu ekstra saat agen memperbaiki celah pengujian/build dari Attempt 1. |
| **Worker Terminal** | Attempt 3+ (Hard Cap) | 25 menit | **45 menit (Cap)** | Batas waktu tertinggi absolut untuk penuntasan tugas kompleks sebelum evaluasi final. |
| **Worker Terminal** | Termination Grace Period | 20 detik | **30 detik** | Jendela pelepasan resource & durable lock secara bersih setelah sinyal SIGTERM. |
| **Terminal Session** | Idle Timeout | 10 menit | **30 menit** | Mencegah sesi terminal interaktif mati mendadak saat user sedang meninjau progress. |

### 2. Protokol Terminasi Dua Tahap (Two-Stage Graceful Termination)
1. **Tahap 1 (Sinyal SIGTERM)**: Saat durasi timeout tercapai, konteks eksekusi dibatalkan (`context.WithTimeout`). Worker mengirimkan sinyal santun `SIGTERM` ke seluruh process group child.
2. **Tahap 2 (Grace Period 30 Detik)**: Worker menunggu hingga 30 detik untuk memberikan kesempatan bagi proses menyimpan berkas sementara dan melepaskan lock file durable pada sistem operasi.
3. **Tahap 3 (Eskalasi SIGKILL)**: Jika proses tidak berhenti setelah 30 detik, worker mengeksekusi sinyal tegas `SIGKILL` untuk memastikan tidak ada runaway process atau zombie process yang membebani memori server.

### 3. Standar Lean Code & Modularitas
- **Modularitas & Pemisahan Tanggung Jawab**: Seluruh modul runner, dispatcher, dan evaluator dipisah menjadi berkas terfokus dengan tanggung jawab tunggal. Tidak ada berkas monolitik tak terkendali.
- **Kompilasi & Targeted Test Kilat**: Seluruh targeted unit test Go untuk dispatcher, runner, dan chat handler wajib tuntas dalam waktu <10 detik pada lingkungan sandbox lokal.
- **Zero Dead Code**: Tidak ada fungsi rintisan (*stubs*), komentar usang, atau dependensi eksternal tanpa fungsi nyata yang dibiarkan di dalam basis kode.

## Risiko, Batasan & Mitigasi

1. **Risk: Worker cuan-runner Tidak Mengambil Task Akibat Ketidakcocokan RunnerID**:
   - *Dampak:* Task attempt berstatus `queued` namun tidak pernah diklaim oleh worker, menyebabkan tugas menggantung tanpa proses.
   - *Mitigasi:* Standarisasi nilai konstanta runner ID menjadi `"cuan-runner"` secara konsisten di seluruh dispatcher (`task_launch_queue.go`, `terminal_handlers.go`, `inbox_delegation.go`) dan tambahkan unit test assertion untuk memvalidasi fungsi `ClaimNextQueuedAttempt`.
2. **Risk: Drain Flag `/tmp/cuan-drain` Tertinggal Pasca Deployment Gagal atau Sebagian**:
   - *Dampak:* Worker baru mengira sistem masih dalam kondisi drain sehingga menolak mengambil job baru dari antrean database.
   - *Mitigasi:* Implementasikan proteksi ganda pada skrip deploy: pastikan `cleanup_worker_drain()` selalu dipanggil dalam blok `finally` / penutup rilis, serta tambahkan mekanisme timeout pada file drain itu sendiri (misal abaikan jika usia file >15 menit) pada logika internal `drain.go`.
3. **Risk: Eskalasi Waktu Eksekusi Menimbulkan Potensi Runaway Process**:
   - *Dampak:* Proses eksekusi yang mengalami infinite loop atau hung membebani CPU dan memori server selama 45 menit sebelum dihentikan.
   - *Mitigasi:* Menerapkan pengawasan progresif ketat dengan hard cap absolut 45 menit, mekanisme terminasi dua tahap (grace period 30 detik untuk pelepasan durable lock disusul SIGKILL paksa), serta idle detection pada I/O terminal.
